# Code Audit实战排障版

> 定位：code-audit 是全局触发链的最终收口技能，不替代实现、测试、DB 设计、安全渗透或发布工程；它负责把“改了什么、影响谁、证据够不够、能否下结论”审清楚。

## 快速总则：变更面 / 调用链 / 证据 / 结论

1. 变更面：先看 diff 范围，再追真实影响面；文件改动、生成代码、配置、依赖、迁移、脚本、路由、权限、缓存 key、队列 topic 都算变更。
2. 调用链：全量搜索生产方、调用方、消费方、旧入口、异步任务、定时任务、Webhook、SDK、前端解析、后台脚本和测试夹具。
3. 证据：每条判断必须绑定 file:line、命令输出、接口样本、测试证据或“未验证”说明；未读不引，未跑不报。
4. 结论：只给四类结论：通过、有阻断风险、有非阻断风险、证据不足；证据不足不能包装成通过。
5. 审计专属目标：发现漏改、错改、偏题、契约漂移、兼容断裂、安全质量回退、测试证据缺口和发布前剩余风险。
6. 默认不扩改：审计只指出最小修复点和联动技能；未经要求不借机重构、补设计或替测试下通过结论。

## 场景执行卡

### 1. 普通代码改动最终收口

- 输入：用户需求、实际 diff、相关提交、运行命令、失败日志、改动前后行为。
- 查变更面：新增/删除/修改文件、入口函数、配置项、依赖版本、生成产物、公共类型、常量、枚举、错误码。
- 查调用链：对改动标识符、接口路径、字段名、事件名、缓存 key、队列 topic 做全量搜索；至少覆盖生产方、调用方、消费方、测试方。
- 查行为：正常路径、空值、边界、异常分支、权限分支、并发分支、回滚/降级分支。
- 结论：需求对账表 + 风险清单 + 证据缺口 + 是否需要回到对应语言/测试/发布链路。

### 2. API、前后端契约与 SDK 消费

- 必查：接口路径、方法、请求字段、响应字段、可空性、枚举值、错误语义、状态码、分页/排序/过滤、版本号、OpenAPI/SDK/Mock。
- 审计重点：前后端契约漂移、旧端兼容、BFF 转换遗漏、默认值变化、字段重命名、数组/对象结构变化、错误体被前端硬解析。
- 证据要求：后端生产方 file:line、前端/APP/SDK 消费方 file:line、样例响应或 contract test 输出。
- 联动边界：契约怎么设计交给 api-design；code-audit 只审是否按既定契约落地、消费者是否全量覆盖、证据是否足够。

### 3. 权限、认证、租户与输入输出边界

- 必查：登录态、角色、scope、租户 ID、资源归属、批量逐项验权、网关头可信边界、服务间身份、管理端和脚本入口。
- 输入输出边界：请求体、query、header、cookie、文件、URL、Webhook、队列消息、环境变量、LLM 输出、第三方回调都按不可信处理。
- 常见结论点：只鉴登录未鉴资源、前端隐藏按钮当权限、批量接口只验首项、内部 header 可被外部伪造、日志/错误泄露敏感信息。
- 联动边界：漏洞复现和安全专项交给 web-security/devsecops；code-audit 审权限链是否因本次改动破口、是否有证据闭环。

### 4. 数据、迁移、事务与兼容

- 必查：表字段、枚举、默认值、NOT NULL、索引、迁移脚本、回填脚本、ORM model、读写路径、旧数据样本、回滚边界。
- 审计重点：迁移兼容、expand-contract 是否保持新旧版本共存、事务边界、锁顺序、唯一约束、幂等键、重试后副作用、软删过滤。
- 证据要求：迁移版本、字段引用搜索、读写双方 file:line、必要时列出未执行的 DB 验证。
- 联动边界：表结构和 SQL 方案交给 db-design；code-audit 审代码是否消费新结构、旧数据是否会炸、测试证据是否覆盖迁移后行为。

### 5. 并发、幂等、异步任务和重试副作用

- 必查：锁、事务、唯一键、幂等 token、状态机、消息去重、定时任务、队列重试、Webhook 重放、超时重试、补偿任务。
- 审计重点：重复扣款/发货/发券/发通知、状态回退、重复创建、乱序消息、部分失败后重试扩大副作用、任务可见性延迟。
- 证据要求：状态流转 file:line、幂等条件、失败分支、重试策略、是否有测试或手动验证证据。
- 联动边界：压测和并发测试设计交给 test-engineering/perf-engineering；code-audit 负责指出需要覆盖的并发失败模式。

### 6. 日志、错误语义、可观测性和排障证据

- 必查：错误码、异常转换、用户可见文案、日志级别、trace/span、request id、审计日志、敏感字段脱敏。
- 审计重点：吞异常、把业务失败记成功、错误语义改变导致前端误判、日志泄露 token/PII、异步链路丢 trace。
- 证据要求：错误抛出点、转换点、消费点、日志样例或未验证说明。
- 联动边界：指标、告警、SLO、dashboard 交给 observability-sre；code-audit 审本次改动是否保留可定位证据。

### 7. 依赖、供应链、生成代码与 AI 生成代码

- 必查：package/lockfile、依赖升级、构建插件、GitHub Actions、容器镜像、生成代码、脚手架、AI 生成片段、license 和 transitive dependency。
- 审计重点：2024-2026 供应链投毒、typosquatting、postinstall、锁文件漂移、构建时远程拉脚本、AI 生成代码的伪 API/伪字段/缺失错误处理。
- 证据要求：版本变更、调用点、构建/测试输出、无法验证的外部风险。
- 联动边界：SCA/SBOM/签名门禁交给 devsecops/release-engineering；code-audit 审依赖变化是否和代码改动匹配、风险是否被记录。

### 8. 修复后复验与全局收口

- 回原路径：原 bug 复现路径、修复路径、相邻入口、旧入口、异常入口都要交代。
- 查漏改：同名函数、重载、monorepo workspace、生成目录、移动端/后台端、管理端、脚本任务。
- 查证据：测试命令、lint/build、手动样例、日志、接口返回；未跑必须写原因。
- 下结论：阻断项必须可复现或有明确代码证据；非阻断项必须说明影响面和建议归属。

## 高频坑 / 防遗漏

### 高频坑

1. 只看 diff，不搜调用方和消费方。
2. 只审新入口，忘了旧路由、后台脚本、定时任务、Webhook 和移动端。
3. 字段改名只改后端，前端/SDK/Mock/OpenAPI 继续用旧字段。
4. 枚举新增后未审默认分支，前端显示 unknown 或后端落到错误状态。
5. 配置 key 改了，环境变量、CI secret、Helm、文档样例和本地默认值未同步。
6. 只看 happy path，不审空值、异常、权限、并发、幂等和事务失败。
7. 队列/重试/补偿任务未审副作用，导致重复通知、重复扣款或状态回退。
8. 迁移脚本存在但代码未兼容旧数据或新旧版本并行。
9. 测试跑了但不覆盖本次风险点，仍写“测试通过”。
10. 日志和错误语义改变，排障链路断了或敏感信息外泄。
11. 依赖升级只看直接包，未看 lockfile、postinstall、构建插件和许可证。
12. AI 生成代码看似能跑，但 API、字段、异常分支、权限判断是幻觉。

### 防遗漏清单

- diff 范围：文件、公共类型、常量、枚举、配置、路由、依赖、脚本、迁移、生成代码是否全列出？
- 调用链：生产方、调用方、消费方、测试方、异步方、旧入口是否全量搜索？
- 契约：接口/字段/错误语义/状态码/可空性/默认值/版本兼容是否一致？
- 数据：旧数据、迁移兼容、事务、锁、唯一约束、幂等键、回滚边界是否审到？
- 权限：资源归属、租户隔离、批量逐项验权、可信 header、后台入口是否覆盖？
- 输入输出边界：外部输入到危险点、输出到用户/日志/第三方是否有校验和脱敏？
- 异步：任务、队列、重试、补偿、乱序、重复投递、副作用是否审到？
- 证据：测试证据、命令输出、file:line、样例响应、未验证项是否分开写？

## 输出要求

1. 审计范围：列出已读 diff、文件范围、版本/分支、用户需求、未覆盖范围。
2. 需求对账：每个需求点给状态：已落地、部分落地、未落地、证据不足；必须附 file:line。
3. 影响面：列生产方、调用方、消费方、配置、数据、异步、测试、发布/观测相关影响。
4. 风险清单：按阻断/非阻断/需验证分级；每条包含证据、失败模式、影响、最小建议、归属技能。
5. 命令产出：列实际跑过的 grep/lint/build/test/接口验证命令和结果；未跑写原因。
6. 结论：只能写通过、有阻断风险、有非阻断风险、证据不足；不得用“应该没问题”。
7. 后续：需要联动 api-design、db-design、test-engineering、web-security、devsecops、release-engineering、observability-sre 时只写触发原因和收口标准。

## 约束

- 不做无证据高危结论；不把未验证写成已验证。
- 不替代 test-engineering 设计和执行测试；只能审测试证据是否覆盖风险。
- 不替代 web-security 渗透复现；只能审本次改动是否引入明显安全风险或需联动。
- 不替代 db-design 设计表/索引/迁移；只能审代码与迁移兼容、调用面和风险证据。
- 不替代 api-design 定契约；只能审契约实现、消费方和兼容证据。
- 不替代 release-engineering 上线；只能审发布前剩余风险、配置/迁移/回滚是否有证据。
- 不替代 observability-sre 建观测体系；只能审日志、错误语义和 trace 是否支持定位。
- 不因审计顺手重构；修复必须最小化且回到对应语言技能，最后再由 code-audit 收口。

## 高频 Bug 反例库

- 反例 1：只看 diff。错法：只审改动文件。对法：按标识符、路由、字段、配置全量搜索调用方和消费方。根因：风险常发生在未改但被影响的代码。
- 反例 2：字段重命名漏前端。错法：后端把 user_name 改成 name 就收口。对法：审前端、APP、SDK、OpenAPI、Mock 和测试夹具。根因：契约漂移不会在后端单测里暴露。
- 反例 3：新增枚举无默认分支。错法：只在后端允许新枚举。对法：审所有 switch/if、显示文案、状态机和导出。根因：消费方默认分支常被当“不可能”。
- 反例 4：只鉴登录。错法：接口有 auth middleware 就判安全。对法：审资源归属、租户、角色、scope、批量逐项验权。根因：认证不等于授权。
- 反例 5：批量操作只验首项。错法：校验第一个 id 后批量更新。对法：逐项验权、逐项状态校验、失败语义明确。根因：集合输入扩大越权面。
- 反例 6：重试导致重复副作用。错法：HTTP/队列失败就自动重试。对法：审幂等键、唯一约束、状态机和补偿任务。根因：重试语义和业务副作用未绑定。
- 反例 7：事务边界错。错法：写主表成功后异步写明细，失败仍返回成功。对法：审事务、补偿、可见性和错误语义。根因：数据一致性跨越函数边界。
- 反例 8：迁移不兼容旧版本。错法：新增 NOT NULL 字段后立即读写新字段。对法：expand-contract、默认值、旧数据回填、新旧代码共存。根因：部署不是瞬时全量切换。
- 反例 9：配置只改本地。错法：改默认配置后不查 CI、容器、Helm、生产 secret。对法：审所有环境来源和发布证据。根因：配置实际值不在代码 diff 里。
- 反例 10：测试证据错配。错法：跑全量测试就说覆盖本 bug。对法：把测试命令映射到需求点、失败模式和回归路径。根因：通过的测试不等于覆盖的风险。
- 反例 11：日志泄密。错法：为排障打印 token、cookie、手机号、身份证或完整请求体。对法：脱敏、降级日志、限制采集边界。根因：调试便利压过安全边界。
- 反例 12：错误语义漂移。错法：把 403 改成 404 或统一 200，前端误判成功。对法：审错误码、状态码、错误体和消费方分支。根因：错误也是契约。
- 反例 13：依赖升级只看 package。错法：只读 package.json。对法：审 lockfile、传递依赖、postinstall、构建插件和运行路径。根因：供应链风险常在间接依赖。
- 反例 14：AI 生成代码未验事实。错法：接受 AI 写出的 API、字段、异常类。对法：查框架文档或项目既有用法，跑最小验证。根因：AI 容易生成语法正确但语义不存在的代码。
- 反例 15：异步任务丢上下文。错法：同步链路有权限和 trace，入队后默认继承。对法：审消息载荷、租户、操作者、幂等键和 trace 传播。根因：异步边界会切断上下文。

## 2024-2026 新坑速查

- 供应链：typosquatting、依赖接管、恶意 postinstall、构建插件投毒、GitHub Actions 版本漂移、容器基础镜像 CVE。
- 依赖治理：只升直接依赖不够；lockfile、transitive dependency、license、运行时加载路径和构建时脚本都要审。
- AI 生成代码：伪 API、伪字段、伪错误类型、缺少权限/异常/并发分支；必须用项目证据或官方资料验证。
- 前后端契约漂移：BFF、GraphQL resolver、SDK、Mock、OpenAPI、移动端缓存 schema 会滞后于后端。
- 异步任务：队列重试、Webhook 重放、定时补偿、乱序消息和延迟可见性会放大副作用。
- 数据迁移：expand-contract、双写/回填/读旧兼容、灰度期间新旧版本共存是默认审计点。
- 权限边界：BOLA/IDOR、租户串用、批量逐项验权、可信 header 清洗、服务间 token audience 是高频漏点。
- 日志与隐私：排障日志、AI prompt、第三方上报、trace baggage 可能泄露 token、PII 或商业数据。
- 构建产物：生成代码、tree shaking、edge runtime、serverless 冷启动和环境变量注入可能让源码审计结论失效。
- 测试证据：CI 通过但 flaky、跳过、缓存命中、Mock 过度、未跑迁移和未覆盖旧端都不能算审计通过。

## 与相邻技能的边界

- test-engineering：负责测试策略、场景矩阵、自动化、flaky、CI 证据；code-audit 负责审测试证据是否覆盖本次风险并作为最终收口输入。
- web-security：负责 Web/API 漏洞复现、攻击面和修复验证；code-audit 负责从代码变更发现需联动的认证、授权、输入输出和泄露风险。
- api-design：负责 API 契约、状态码、版本兼容、幂等原则和文档；code-audit 负责审契约实现、调用方/消费方同步和契约漂移证据。
- db-design：负责表、字段、索引、SQL、事务模型、迁移和数据修复方案；code-audit 负责审代码影响面、迁移兼容、旧数据和证据缺口。
- devsecops：负责 SAST/DAST/SCA/SBOM、secrets、签名、CI/CD 安全门禁和供应链治理；code-audit 负责识别依赖/构建变化是否引入需门禁的风险。
- release-engineering：负责构建物、环境、灰度、回滚、冒烟、监控告警和发布证据；code-audit 负责把配置、迁移、兼容和剩余风险交给发布链路。
- observability-sre：负责线上症状、日志/指标/链路、SLO、告警和 incident；code-audit 负责审本次改动是否保留可定位的日志、错误语义和 trace 上下文。
- project-learning：负责陌生项目入口、架构、调用链、数据流和约定学习；code-audit 在其证据基础上做最终需求对账和影响面收口。
